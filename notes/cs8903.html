    Foundational Reading on UAV Firmware Verification

    Reading notes on three foundational papers covering the static, runtime, and patch axes of cyber-physical security for unmanned aerial vehicle (UAV) firmware. Each paper attacks a different stage of the post-deployment firmware audit pipeline. These notes focus on the technical mechanics of each paper — the algorithms, the data structures, and the mathematical objects they operate on — rather than on a survey-level overview.

    Topics

    1. Background — Control, Stripped Binaries, IEEE-754
    2. MISMO — Identifying PID Methods in Stripped Binaries
    3. MAYDAY — Post-Accident Investigation via CVDG
    4. DisPatch — A DSL for In-Field Firmware Patches
    5. How the Three Papers Compose

    0. Background — Control, Stripped Binaries, IEEE-754

    Six pieces of background let every following section sit precisely: the discretised PID equations, the anti-windup and derivative-filter modifications used in production firmware, the two-tier cascade architecture, what SITL gives us, why stripped binaries are the realistic audit target, and the IEEE-754 floating-point model that all later verification rests on.

    0.1 PID Control, Continuous and Discrete

    The classical proportional-integral-derivative controller takes an error signal $e(t) = r(t) - y(t)$ (reference minus measurement) and produces an actuator command:

    $$u(t) = K_p\, e(t) + K_i\!\!\int_0^t\! e(\tau)\,d\tau + K_d\,\dot{e}(t)$$

    On a real UAV this is discretised at a fixed rate $\Delta t$ (typically 2.5 ms for the inner attitude loop, 20 ms for the outer position loop). The integral becomes a Riemann sum and the derivative becomes a backward difference:

    $$u_n = K_p\, e_n + K_i \sum_{k=0}^{n} e_k\,\Delta t + K_d \frac{e_n - e_{n-1}}{\Delta t}$$

    In code this is typically expressed incrementally so the integrator state $I_n$ is kept across calls:

    $$I_n = I_{n-1} + K_i\, e_n\, \Delta t, \qquad u_n = K_p\, e_n + I_n + K_d \frac{e_n - e_{n-1}}{\Delta t}$$

    0.2 Anti-Windup and Derivative Filtering

    Two production-firmware modifications matter because they show up as additional structure in every reverse-engineered PID method:

    Anti-windup (back-calculation). When the actuator saturates ($u_n$ clipped to $[u_\text{min}, u_\text{max}]$), the integrator should not keep accumulating error or it will overshoot wildly on the way back into range. The common fix is back-calculation:

    $$I_n = I_{n-1} + K_i\, e_n\, \Delta t + K_t\,(u_n^\text{sat} - u_n^\text{unsat})$$

    where $K_t > 0$ pushes the integrator back when saturation is detected.

    Derivative low-pass. The raw backward-difference derivative amplifies sensor noise. Production code low-pass-filters $\dot{e}$ with a single-pole filter parameterised by a time constant $\tau$:

    $$\dot{e}_n^\text{filt} = \alpha\, \dot{e}_n + (1 - \alpha)\, \dot{e}_{n-1}^\text{filt}, \qquad \alpha = \frac{\Delta t}{\tau + \Delta t}$$

    This is the T_lpf term that appears in AC_PID and the various D_FILT parameters in ArduPilot. From a verification perspective, the filter coefficient $\alpha$ is computed on every call from $\tau$ and $\Delta t$; it is not a stored constant. Any symbolic equivalence proof on a PID method has to account for the filter's incremental form.

    0.3 The Two-Tier Control Architecture

    Modern open-source flight stacks (ArduPilot, PX4) all use a two-tier cascade:

    TierRateLoopsSetpoint → Measured
    Outer (Position / Velocity)~50 HzAC_PosControl, AC_PID_2Dtarget NE position → commanded acceleration
    Inner (Attitude / Rate)~400 HzAC_AttitudeControl, AC_PIDtarget rate → motor PWM

    The two tiers are coupled: the outer-loop output is the inner-loop setpoint. A bug in the outer loop manifests at the inner loop's input; a bug in the inner loop manifests at the actuator. This matters for forensics — the symptom (which channel exhibits anomalous statistics) is several control-loop hops downstream of the root cause.

    0.4 SITL: Software-In-The-Loop Simulation

    SITL is the same firmware binary you would flash to a real Pixhawk, compiled for an x86_64 or aarch64 host, with sensor drivers replaced by a simulated physics engine. From a research standpoint this is the ideal substrate: the binary under test is identical to the deployed one, but inputs are reproducible and outputs are inspectable. Both ArduPilot and PX4 ship official SITL builds; the three papers in this reading all run their evaluations in SITL.

    0.5 Why Stripped Binaries

    Two reasons. First, operational reality: when a UAV crashes or is recovered after an incident, the only artefact an investigator reliably has is the flashed image, usually with debug symbols stripped to save flash space. Second, the threat model: a supply-chain attacker who has tampered with the firmware will not leave symbol tables behind. Audit tooling that depends on nm-style output is useless against this adversary. All three papers in this reading operate under this constraint: the only thing the analyst is allowed to read is a sequence of bytes that decodes to ARM Cortex-M Thumb-2 instructions.

    0.6 IEEE-754 in 90 Seconds

    Every floating-point value in a PID controller is a 32-bit IEEE-754 single-precision float (binary32). The bit layout is:

    $$\underbrace{s}_{\text{1 bit sign}}\; \underbrace{eeeeeeee}_{\text{8 bit exponent}}\; \underbrace{mmmmmmmmmmmmmmmmmmmmmmm}_{\text{23 bit mantissa}}$$

    Encoding a normalised value: $(-1)^s \cdot 1.m \cdot 2^{e - 127}$. Floating-point addition and multiplication are non-associative: $(a + b) + c \neq a + (b + c)$ in general, because rounding happens at every operation. This is the entire reason bit-exact verification of two compiled versions of the same equation is non-trivial: two different orderings of the same arithmetic produce different bit patterns even though the mathematical value they approximate is the same.

    The IEEE-754 standard distinguishes special values: $+0$ and $-0$ (different bit patterns, but $+0 = -0$); subnormals (very small numbers below $2^{-126}$); $+\infty$, $-\infty$, and NaN (with quiet vs signalling variants). Any equivalence verifier has to handle each special-value class explicitly; an SMT theory of floating-point arithmetic (FPA, specifically QF_FP) gives this for free.

    1. MISMO — Identifying PID Methods in Stripped Binaries

    Paper: Pengfei Sun, Luis Garcia, Saman Zonouz. “MISMO: Multi-Stage Inspection of Mission-Critical Operations on Drones.” DSN 2019. (Rutgers)

    Goal: Given a stripped ArduPilot or PX4 ELF (no symbols, no function names — what an attacker or auditor actually obtains), identify which functions implement the mission-critical PID control loops, so that downstream tooling can verify, fuzz, or patch them.

    1.1 The Problem, Concretely

    A modern ArduCopter ELF, stripped, contains roughly 800–1000 functions, every one named sub_XXXXXX. PID controllers are small (about fifty lines each), heavily floating-point, and structurally similar to a half-dozen other routines: the EKF measurement update, the complementary filter, the motor mixer, the coordinate transform between body and NED frames. Brute-forcing symbolic execution on every candidate is infeasible — each path can take minutes, and the path count is exponential in branch depth. MISMO's contribution is a three-stage pipeline that progressively shrinks the candidate set by orders of magnitude using progressively more expensive analyses.

    1.2 The Pipeline at a Glance

    1.3 Phase A — Static Binary Feature Filter

    Phase A treats every function as a bag of instructions and scores it by two binary features:

    1. FP density. Define the FP density of a function $f$ as $$\rho_\text{fp}(f) = \frac{|\{i \in f : \text{op}(i) \in \mathcal{F}\}|}{|f|}$$ where $\mathcal{F} = \{\texttt{vadd.f32}, \texttt{vsub.f32}, \texttt{vmul.f32}, \texttt{vfma.f32}, \texttt{vdiv.f32}, \texttt{vcvt.f32}, \texttt{vldr}, \texttt{vstr}\}$ is the VFPv4 instruction set and $|f|$ is the function's total instruction count.
    2. this-pointer access. Define a predicate $\text{hasThis}(f) = 1$ if at least one instruction in $f$ reads from [r0, #k] for some $k$ in a small offset range (typically $0 \leq k \leq 256$, word-aligned). The ARM C++ ABI passes the implicit this pointer in r0; a class method dereferencing this->member produces exactly this access pattern.

    The filter retains $f$ iff $|f| \cdot \rho_\text{fp}(f) \geq 5$ and $\text{hasThis}(f)$.

    Pseudo-algorithm (using angr for CFG construction and capstone for instruction decoding):

    def phase_a(elf_path, fp_density_min=5, this_ptr_offsets=range(0, 256, 4)):
    proj = angr.Project(elf_path, auto_load_libs=False)
    cfg  = proj.analyses.CFGFast()
    candidates = []

    for fn in cfg.functions.values():
        insns = list(fn.instructions())
        if len(insns) < 10:
            continue   # too small to be a PID

        fp_count = sum(1 for i in insns
                       if i.mnemonic.startswith(('vadd', 'vmul', 'vsub',
                                                  'vfma', 'vdiv', 'vcvt')))
        if fp_count < fp_density_min:
            continue

        has_this = any(insn_reads_offset_of(i, reg='r0', offsets=this_ptr_offsets)
                       for i in insns)
        if not has_this:
            continue

        candidates.append((fn.addr, fp_count))

    return sorted(candidates, key=lambda x: -x[1])  # rank by FP density

    Why these two features? They're the two structural invariants a PID method must satisfy: it does dense math (PID is by definition $K_p e + K_i \int e + K_d \dot{e}$) and it stores state across calls (the integrator, the previous error) which it reads off this. A function failing either test cannot be a PID; a function passing both might be.

    1.4 Phase B — Dynamic Taint Propagation

    Phase A keeps every function that looks like a PID structurally. Phase B asks whether it behaves like one. The firmware is run in SITL with sensor inputs (gyroscope axes, accelerometer axes, GPS velocity components) labelled with taint colours. Taint is propagated forward through the call graph by the following rule: when an instruction reads tainted operands and writes a destination, the destination inherits the union of the source taints.

    For a candidate $f$ to survive Phase B, two predicates must hold over an execution trace:

    $$\text{reachable}_\text{sensor}(f) \;\wedge\; \text{reachable}_\text{motor}(f)$$

    where

    • $\text{reachable}_\text{sensor}(f) = $ true iff some tainted value enters $f$ during the trace;
    • $\text{reachable}_\text{motor}(f) = $ true iff some value $f$ writes eventually reaches the motor-mixer output channel.

    Pseudo-algorithm sketch:

    def phase_b(elf, phase_a_candidates, trace_log, taint_sources, taint_sinks):
    taint_map = {}  # address -> set of taint labels seen there
    propagate_taint(trace_log, taint_sources, taint_map)

    survivors = []
    for fn_addr in phase_a_candidates:
        reads_tainted  = any(taint_map.get(a, set()) for a in fn_reads(fn_addr))
        writes_to_sink = any(reachable(out, taint_sinks) for out in fn_writes(fn_addr))
        if reads_tainted and writes_to_sink:
            survivors.append(fn_addr)
    return survivors

    This typically collapses the set by another order of magnitude, from 50–100 to under 10, by eliminating EKF inner-state methods (they read sensors but their outputs feed back into other EKF stages, not directly to motors) and motor-mixing logic (it writes motors but its inputs are already-PID-computed setpoints).

    1.5 Phase C — SE + SMT AST Matching

    Phase C is the most expensive and the most precise. For each surviving candidate, MISMO:

    1. Symbolically executes the function from its entry point, treating inputs (member variables loaded from this, register-passed arguments) as symbolic variables.
    2. Captures the AST of the output expression returned by the function.
    3. Compares the captured AST against a library of PID template ASTs by asking an SMT solver whether the two expressions are equivalent for all inputs.

    The template library encodes the canonical algebraic forms of $K_p e$, $K_p e + I$, $K_p e + I + K_d (e - e_\text{prev})$, the filtered-derivative variant, etc. For each template $T$, the SMT query is:

    $$\forall\, \mathbf{x} \in \mathbb{F}_{32}^n.\; f_\text{captured}(\mathbf{x}) = T(\mathbf{x})$$

    which, by the standard trick, is encoded by asking the SMT solver to find a counterexample to:

    $$\exists\, \mathbf{x}.\; f_\text{captured}(\mathbf{x}) \neq T(\mathbf{x})$$

    An UNSAT answer means the captured function is equivalent to template $T$ (over all 32-bit FPA inputs). A SAT answer returns a concrete counter-example $\mathbf{x}^*$.

    Intuition for the three stages: Phase A asks “does it look like a PID?”, Phase B asks “does it behave like one?”, Phase C asks “is its algebra equal to a PID template?” Each stage is necessary but not sufficient on its own — this is the recurring lesson.

    1.6 The Limiting Cases of Phase C

    Phase C can fail to match a true PID under two conditions:

    • Algebraic non-equivalence at bit level. A compiler may emit $(K_p e + I) + K_d d$ on one binary and $K_p e + (I + K_d d)$ on another. Mathematically these are equal; in IEEE-754 FPA they are not. The template library must contain both ordering variants, or the SMT match returns SAT with a counter-example that is really just floating-point round-off noise.
    • Compiler inlining. If the compiler has inlined helper functions (e.g., the derivative low-pass into the call site), the captured AST grows past the template's surface and SMT may time out without resolving SAT or UNSAT.

    Both failure modes show up in practice; MISMO's mitigation is to expand the template library to cover compiler variants and to set a generous SMT timeout (typically minutes per query) with a fall-back rule of “timeout = no match”.

    1.7 The Structural Lesson

    Before MISMO, the dominant approach to PID identification was either symbol-table extraction (useless against stripped binaries) or source-code instrumentation (useless against deployed firmware). MISMO's contribution is showing that the gap between “I have the binary” and “I can verify which functions are PIDs” can be closed entirely with off-the-shelf binary-analysis primitives, with no source, no symbols, no traces, and no co-operation from the manufacturer.

    The cheap-static-then-expensive-semantic layering is the structural lesson worth carrying to other CPS audit problems.

    2. MAYDAY — Post-Accident Investigation via CVDG

    Paper: Taegyu Kim, Chung Hwan Kim, Altay Ozen, Fan Fei, Zhan Tu, Xiangyu Zhang, Xinyan Deng, Dave (Jing) Tian, Dongyan Xu. “MAYDAY: Identifying Post-Accident Investigation Targets for Drones.” USENIX Security 2020. (Purdue)

    Goal: After a drone crash, given only (i) the last seconds of telemetry from the flight log and (ii) the firmware ELF, point an investigator at the parameter or code change that caused the crash — instead of asking them to manually inspect the ~1000 tunable parameters of a modern flight stack.

    2.1 Why This Is Hard

    ArduCopter exposes roughly 1000 user-tunable parameters: gains (ATC_RAT_PIT_P), filter time constants (ATC_INPUT_TC), failsafe thresholds (BATT_LOW_VOLT), sensor calibrations, geofence radii. Any one of them, set out of range, can crash a drone — often through subtle multi-loop interactions where the surface symptom is several control-loop hops downstream of the root cause. The forensic correlation problem — this telemetry symptom → that parameter — is exactly what MAYDAY automates.

    2.2 The Core Data Structure: Control-Variable Dependency Graph

    The CVDG is the heart of MAYDAY. It is a directed graph $G = (V, E)$ where $V$ is a typed set of nodes:

    CVDG node types:
    • Parameter nodes — user-tunable values exposed over MAVLink (e.g., ATC_RAT_PIT_P).
    • Internal state nodes — private member variables of control classes (e.g., _pitch_error, _integrator).
    • Method nodes — binary addresses of identified control methods (e.g., the address of AC_PID::update_all).
    • Output channel nodes — telemetry-observable outputs (e.g., motor_pitch_out, vel_y).

    And $E$ carries four edge types, encoding the dependency direction:

    Edge typeDirectionMeaning
    param_ofparameter → methodthis method reads this parameter at runtime
    binds_toMAVLink name → internal varaliasing across the MAVLink boundary
    produces_formethod → output channelthis method writes this telemetry channel
    read_byvariable → methodthis method reads this variable

    2.3 Building the CVDG From a Binary

    Construction is offline and one-time per firmware version. The algorithm:

    def build_cvdg(elf_path, mavlink_param_table, identified_methods):
    G = DirectedGraph()

    # (1) Add parameter nodes from the firmware's MAVLink parameter table.
    for pname in mavlink_param_table:
        G.add_node(pname, type="parameter")

    # (2) Add method nodes from MISMO-style identification (or symbol table
    #     if available; the paper handles both stripped and unstripped).
    for method_addr, method_name in identified_methods:
        G.add_node(method_addr, type="method", label=method_name)

    # (3) Walk every method's binary to discover its reads and writes.
    for method_addr, _ in identified_methods:
        for insn in disassemble(method_addr):
            for src in operand_reads(insn):
                if is_member_load(src):
                    var = resolve_this_offset(src)
                    G.add_node(var, type="internal_state")
                    G.add_edge(var, method_addr, type="read_by")
            for dst in operand_writes(insn):
                if is_output_channel(dst):
                    G.add_edge(method_addr, dst, type="produces_for")

    # (4) Add binds_to edges from the MAVLink parameter table.
    #     This handles historical aliases (PSC_VELXY_D, PSC_NE_VEL_D, ...).
    for pname, internal_var, *aliases in mavlink_param_table:
        for name in [pname, *aliases]:
            G.add_edge(name, internal_var, type="binds_to")

    return G

    The binds_to edges are more important than they look. MAVLink parameter names and internal C++ member names diverge across firmware revisions: the position-loop velocity D-gain is called PSC_VELXY_D in MAVLink dumps but stored as _velxy_d internally; in earlier versions it was PSC_NE_VEL_D. Without enumerating these aliases, the reverse-walk reaches the internal variable and stops, never reaching the MAVLink name that the investigator actually sees in the flight log.

    2.4 Anomaly Detection

    Two flights of identical mission profile are run: a baseline (Phase A) on the audited firmware and a suspect (Phase B) on the firmware in question. For each instrumented telemetry channel $c$, MAYDAY extracts a statistic $s_c(\text{log})$ — typically the standard deviation $\sigma$ of the channel over a fixed window. An anomaly is declared on channel $c$ iff:

    $$s_c(\text{log}_\text{B}) > T_c \quad\text{and}\quad \frac{s_c(\text{log}_\text{B})}{s_c(\text{log}_\text{A})} > R$$

    where $T_c$ is the per-channel absolute threshold (calibrated from known-good flights) and $R$ is a multiplicative-ratio threshold (typically $R \approx 1.4$). The ratio condition prevents false positives on naturally noisy channels.

    Each declared anomaly type maps to a fixed seed method in the CVDG:

    CHANNELS = {
    "pitchspeed_std" : (lambda log: log["ATTITUDE.pitchspeed"].std(),  0.30),  # rad/s
    "vy_std"         : (lambda log: log["LOCAL_POSITION_NED.vy"].std(), 0.025), # m/s
    # ...
}

ANOMALY_TO_SEED = {
    "pitch_rate_oscillation": "AC_PID::update_all",
    "position_loop_drift"   : "AC_PID_2D::update_all",
    "input_shape_jerk"      : "AC_AttitudeControl::input_quaternion",
}

def detect_anomalies(baseline_log, suspect_log, ratio_threshold=1.4):
    anomalies = []
    for name, (extractor, abs_threshold) in CHANNELS.items():
        base = extractor(baseline_log)
        susp = extractor(suspect_log)
        if susp > abs_threshold and susp / base > ratio_threshold:
            anomalies.append(anomaly_type_for(name))
    return anomalies

    2.5 CVDG Reverse-Walk

    Given a seed method node $m_0$, MAYDAY performs a breadth-first search backwards through read_by and binds_to edges, accumulating distances. Each path back to a parameter node contributes one ranking entry, scored by hop count:

    def reverse_walk(cvdg, seed_method, max_hops=8):
    visited = {seed_method: 0}
    queue   = deque([seed_method])
    while queue:
        node = queue.popleft()
        if visited[node] >= max_hops:
            continue
        for predecessor in cvdg.predecessors(
            node, edges={"read_by", "binds_to"}
        ):
            if predecessor not in visited:
                visited[predecessor] = visited[node] + 1
                queue.append(predecessor)
    return sorted(
        [(n, hops) for n, hops in visited.items()
                   if cvdg.node_type(n) == "parameter"],
        key=lambda x: x[1]
    )

    The output is a top-K list of candidate parameters ordered by hop distance from the seed (ties broken arbitrarily or by the lexicographic order of the parameter name).

    2.6 The Conceptual Trick

    What makes the CVDG work: the graph is built statically (from the firmware ELF) but is indexed dynamically (by an anomaly type extracted at runtime from the flight log). The static graph encodes the universe of what could possibly cause each anomaly; the runtime anomaly classifier picks the seed node that says what to walk backwards from. Neither piece alone is enough; together they reduce a 1000-parameter haystack to a small ranked list.

    2.7 Why a Hop-Count Ranking Is Defensible

    MAYDAY's ranking is intentionally simple: shorter paths back to the seed score higher. There are two reasons this works as well as it does in practice:

    1. Control loops have shallow dependency depth. A modern PID method reads about 3–5 parameters directly; another 5–10 are accessible within two hops through composed setpoints. Anything more than four hops away is usually a different control axis or a different subsystem entirely.
    2. Ranking is conservative by design. A wrong rank-1 wastes a few minutes of an investigator's time; a missed top-10 means MAYDAY failed silently. The shallow walk is biased toward false positives over false negatives.

    The paper reports 75 % bug localisation within four hops on private 3DR IRIS+ and MantisQ crash logs, where the bugs were genuinely unknown at the time of investigation. This is the headline empirical claim.

    3. DisPatch — A DSL for In-Field Firmware Patches

    Paper: Taegyu Kim, Aolin Ding, Sriharsha Etigowni, Pengfei Sun, Jizhou Chen, Luis Garcia, Saman Zonouz, Dongyan Xu, Dave (Jing) Tian. “DisPatch: Identification, Disclosure, and Patching of Drone Firmware Configuration Vulnerabilities.” MobiSys 2022.

    Goal: Apply small, tractable, verifiable patches to deployed drone firmware in the field — without recompiling, without grounding the fleet, and without the risk that a hand-written assembly patch destabilises the flight controller.

    3.1 Why a Domain-Specific Language Is the Right Idea

    The naive alternative — ship a hand-written assembly patch as a hot-swap binary blob — has three failure modes:

    1. No formal semantics. A hand-written patch is just bytes; you can prove nothing about it except by exhaustive testing.
    2. Hard to verify. Symbolic execution on arbitrary assembly is intractable when the patch can touch any register, any memory location, any flag.
    3. Hard to insert in place. Variable-length patches require trampoline schemes whose correctness depends on the patcher knowing about every callsite.

    DisPatch observes that the majority of published RAV firmware patches fall into a very small operational vocabulary: clamp a scalar, replace a value, rate-limit a derivative, log a sensor reading. By restricting patches to a DSL targeted at these primitives:

    • Each operation has formal operational semantics ⇒ verification is tractable.
    • Each operation lowers to a small fixed-size Thumb-2 sequence ⇒ in-place trampoline insertion is straightforward.
    • The patch can be proved bit-exact equivalent to the original binary outside the patch region — the gold-standard correctness statement.

    3.2 The DSL Surface and Its Operational Semantics

    Each operation is defined as a small-step rewrite on the program state $\sigma$ (a map from variable names to IEEE-754 values).

    OperationOperational semantics
    clamp(x, lo, hi)$\sigma' = \sigma[x \mapsto \max(lo, \min(hi, \sigma(x)))]$
    replace(x, v)$\sigma' = \sigma[x \mapsto v]$
    log(x, \phi)$\sigma' = \sigma$;  if $\sigma \models \phi$ then $\text{emit}(\sigma(x))$
    rate_limit(x, M)$\Delta = \sigma(x) - \sigma_\text{prev}(x)$; $\sigma'(x) = \sigma_\text{prev}(x) + \mathrm{sign}(\Delta)\cdot\min(|\Delta|, M\,\Delta t)$
    vec_clamp(\mathbf{v}, lo, hi)Apply clamp to each component of $\mathbf{v}$
    if_clamp(\phi, x, lo, hi)If $\sigma \models \phi$ then apply clamp; else $\sigma' = \sigma$

    Note that rate_limit requires access to the previous-frame value $\sigma_\text{prev}(x)$ and the loop period $\Delta t$. In codegen, $\sigma_\text{prev}(x)$ is stored in a scratch slot in the patch region and updated on every entry; $\Delta t$ is loaded from the firmware's existing scheduler tick variable.

    3.3 Codegen to Thumb-2

    Each DSL statement is lowered to a Thumb-2 instruction sequence. The compiler emits fixed-size sequences so that the patch region size can be computed at parse time. Sample lowerings:

    clamp(x, lo, hi) — assuming $x$ is in s0, $lo$ and $hi$ are immediates loaded into s1, s2:

    vldr.32   s1, =lo         ; load lo from literal pool
vldr.32   s2, =hi          ; load hi
vmin.f32  s0, s0, s2       ; s0 = min(s0, hi)
vmax.f32  s0, s0, s1       ; s0 = max(s0, lo)

    replace(x, v):

    vldr.32   s0, =v          ; load v
vstr.32   s0, [r0, #off]  ; store into x's member slot

    rate_limit(x, M) — assuming $x_\text{new}$ in s0, $x_\text{prev}$ in scratch slot at offset off_prev, $\Delta t$ in s3, $M$ as immediate:

    vldr.32   s1, [r0, #off_prev]   ; s1 = x_prev
vsub.f32  s2, s0, s1              ; s2 = delta = x_new - x_prev
vldr.32   s4, =M                  ; s4 = M
vmul.f32  s4, s4, s3              ; s4 = M * dt
vabs.f32  s5, s2                  ; s5 = |delta|
vcmp.f32  s5, s4                  ; flag: |delta| vs M*dt
vmrs      APSR_nzcv, FPSCR
ite       gt                       ; if |delta| > M*dt
vcpy.f32  s2, s4                  ; then s2 = sign(delta) * M*dt  (after vsel applies sign)
vadd.f32  s0, s1, s2              ; s0 = x_prev + delta_clamped
vstr.32   s0, [r0, #off_prev]   ; write back x_prev for next iteration

    Each operation is a fixed-size block; the compiler's job is to chain blocks, manage the literal pool, and emit a trampoline branch back to the un-patched function body.

    3.4 Trampoline Insertion

    Insertion happens via trampoline at the patched function's entry:

    1. Read the first $k$ bytes of the target function (call this the displaced prologue).
    2. Allocate a patch region in unused flash; place it within branch range.
    3. Write into the patch region: (a) the displaced prologue, (b) the lowered Thumb-2 of the DSL statements, (c) an unconditional branch back to the target at offset $k$.
    4. Overwrite the target's first $k$ bytes with b.w <patch_region>.

    The bit-exact-outside-patch-region property is preserved because every byte outside the trampoline and patch region is byte-identical to the original binary, which can be checked by a byte comparison after the patch is applied. The trampoline takes exactly four bytes (one b.w instruction); $k$ is chosen as 4 in practice.

    3.5 Verification

    For each DSL operation, the paper provides an operational semantic spec in first-order logic over IEEE-754 floats. A patched function's symbolic execution is then checked for two properties:

    Within-patch-region correctness. Let $\llbracket s \rrbracket$ be the denotation of DSL statement $s$ on state $\sigma$. The compiler must guarantee:

    $$\forall \sigma.\; \mathrm{exec}_\text{thumb}(\mathrm{codegen}(s), \sigma) = \llbracket s \rrbracket(\sigma)$$

    which is discharged by symbolic execution of the emitted Thumb-2 against the semantic spec, asking an SMT solver to find a counterexample (UNSAT ⇒ correct).

    Outside-patch-region equivalence. For every input, every byte of the program state outside the patch region is identical to the original binary's state at the same execution point:

    $$\forall \sigma,\, \forall b \notin \mathrm{Region}_\text{patch}.\;\; \mathrm{state}_\text{orig}(\sigma)[b] = \mathrm{state}_\text{patched}(\sigma)[b]$$

    Together these give the strongest possible patch-correctness claim: the patch does what the DSL says and nothing else.

    3.6 The Conceptual Trick

    What makes DisPatch work: domain restriction. By giving up the ability to express arbitrary patches and accepting only a small DSL of clamp/replace/log/rate_limit-style operations, DisPatch buys (a) tractable verification, (b) compact fixed-size codegen, and (c) safe in-place trampoline insertion. The paper's experiments demonstrate that this restricted surface covers most published RAV firmware vulnerabilities — the constraint, in practice, is not binding.

    4. How the Three Papers Compose

    The three papers are usually presented as independent contributions, but they answer three orthogonal questions about the same object — a PID-based UAV control loop running on a stripped binary. The cleanest way to organise them is by the question each one answers:

    PaperQuestion it answersMethodOutput

    Read in the right order, they form a coherent post-deployment audit-and-fix pipeline:

    Each paper assumes the output of the one above it: MAYDAY's CVDG construction needs MISMO-style identification of which functions are PIDs (so that AC_PID::update_all can be a meaningful seed-method node), and DisPatch needs MAYDAY-style root-cause localisation to know which function to patch in the first place.

    4.2 The Recurring Algorithmic Pattern

    Each paper attacks an intractable search space by combining a cheap structural filter with an expensive semantic check. The three patterns are structurally homologous:

    PaperCheap structural filterExpensive semantic check
    MISMOFP density + this-ptr (Phase A)SE + SMT AST matching (Phase C)
    MAYDAYPer-channel statistical anomalyCVDG reverse-walk over typed edges
    DisPatchDSL-restricted patch surfaceSMT-discharged within-region correctness + outside-region equivalence

    This is the structural lesson of the reading: the right unit of contribution in this field is not a single clever algorithm but a layered pipeline that uses cheap signals to narrow the search space for expensive analyses. Every successful tool I have encountered in the cyber-physical-security literature recapitulates this layering with different ingredients per stage.
