    Foundational Reading on UAV Firmware Verification

    Directed reading on three foundational papers covering the static, runtime, and patch axes of cyber-physical security for unmanned aerial vehicle (UAV) firmware, paired with local code-level reproductions on ArduPilot and PX4 in software-in-the-loop simulation. Each paper attacks a different stage of the post-deployment firmware audit pipeline; together they form a layered methodology that anchors the broader CS 8903 project on bit-exact IEEE-754 PID equivalence verification.

    0. Background — Why UAV Firmware Is Hard to Audit

    Before any of the three papers makes sense, four pieces of context are non-negotiable: what a PID controller is, how it's organized in a modern UAV stack, what software-in-the-loop (SITL) simulation gives us, and why stripped binaries are the practical attack and audit target.

    0.1 PID Control in 60 Seconds

    The classical proportional-integral-derivative controller takes an error signal $e(t) = r(t) - y(t)$ (reference minus measurement) and produces an actuator command:

    $$u(t) = K_p\, e(t) + K_i\!\!\int_0^t\! e(\tau)\,d\tau + K_d\,\dot{e}(t)$$

    On a real UAV, this is discretised at a fixed rate (typically 400 Hz for the inner attitude loop, 50 Hz for the outer position loop) and the integral and derivative are replaced by their numerical equivalents:

    $$u_n = K_p\, e_n + K_i \sum_{k=0}^{n} e_k\,\Delta t + K_d \frac{e_n - e_{n-1}}{\Delta t}$$

    In ArduPilot, each axis (roll, pitch, yaw rate, …) gets its own AC_PID instance. The integrator and derivative are usually post-processed by a low-pass filter on the derivative (the “D” term is notoriously noise-prone) and by anti-windup logic on the integrator. The actual AC_PID::update_all method in ArduPilot is ~50 lines of dense floating-point code — small enough to symbolically execute, large enough to make recognition non-trivial.

    0.2 The Two-Tier Control Architecture

    Modern open-source flight stacks (ArduPilot, PX4) all use a two-tier cascade:

    TierRateLoopsSetpoint → Measured
    Outer (Position / Velocity)~50 HzAC_PosControl, AC_PID_2Dtarget NE position → commanded acceleration
    Inner (Attitude / Rate)~400 HzAC_AttitudeControl, AC_PIDtarget rate → motor PWM

    This matters because bugs and forensic anomalies are tier-specific: a bad PSC_VELXY_D manifests as outer-loop position drift; a bad ATC_RAT_PIT_P manifests as inner-loop attitude oscillation. The same telemetry channel (say, $v_y$ or $\omega_\text{pitch}$) reveals different failure modes depending on which tier you instrument.

    0.3 SITL: Software-In-The-Loop Simulation

    SITL is the same firmware binary you would flash to a real Pixhawk, compiled for x86_64 or aarch64 host, with sensor drivers replaced by a simulated physics engine. From a verification standpoint this is the perfect substrate: the binary under test is identical to the deployed one, but inputs are reproducible and outputs are inspectable.

    ArduPilot's SITL exposes three physics options:

    OptionInvocationQuality
    Built-in SIH--model + Battle-tested by the ArduPilot team; default for CI
    JSON bridge--model JSONGeneric UDP front-end for external physics (Gazebo, AirSim)
    FlightGear visualiser--enable-fgviewAdds a 3D render layer; physics still runs in SITL

    Throughout my reproductions I rely on the built-in SIH because its PID tuning is shipped with the firmware and known-good. Gazebo's iris airframe ships without a tuned PID set and flies unstably out-of-the-box on stock ArduPilot master — a separate problem that is out of scope for this reading.

    0.4 Why Stripped Binaries

    Two reasons:

    1. Operational reality. When a UAV crashes or is recovered after an incident, the only artefact an investigator reliably has is the flashed image — usually with debug symbols stripped to save flash space.
    2. Threat model. A supply-chain attacker who has tampered with the firmware will not leave symbol tables behind. Audit tooling that requires nm output is useless against this adversary.

    All three papers in this reading operate under this constraint: the only thing you're allowed to read is a sequence of bytes that decodes to ARM Cortex-M Thumb-2 instructions. Anything else — function boundaries, types, names — has to be recovered.

    1. MISMO — Stripped-Binary Identification of PID Methods

    Paper: Pengfei Sun, Luis Garcia, Saman Zonouz. “MISMO: Multi-Stage Inspection of Mission-Critical Operations on Drones.” DSN 2019. (Rutgers)

    Goal: Given a stripped ArduPilot or PX4 ELF (no symbols, no function names — what an attacker or auditor actually obtains), identify which functions implement the mission-critical PID control loops, so that downstream tooling can verify, fuzz, or patch them.

    1.1 The Problem, Concretely

    A modern ArduCopter ELF, stripped, contains roughly 800–1000 functions, every one named sub_XXXXXX. PID controllers are small (~50 lines), heavily floating-point, and structurally similar to a half-dozen other routines: the EKF measurement update, the complementary filter, the motor mixer, the coordinate transform between body and NED frames. Brute-forcing symbolic execution on every candidate is infeasible — each path can take minutes, and the path explosion is exponential. MISMO's contribution is a three-stage pipeline that progressively shrinks the candidate set by orders of magnitude using progressively more expensive analyses.

    1.2 The Architecture

    ┌─────────────────────────────────────────────────────────┐
│  Stripped ELF (~800–1000 functions, sub_xxxxxx names)   │
└──────────────────────────┬──────────────────────────────┘
                           │  Phase A — static FP density + this-ptr
                           ▼
            ~50–100 candidate functions (~10% of input)
                           │  Phase B — dynamic taint (gyro → motor)
                           ▼
                ~5–10 candidate functions
                           │  Phase C — SE + SMT AST match vs PID templates
                           ▼
        Final identification: which template, which axis

    The pattern is generic: cheap static signal first, expensive semantic check last. Every CPS-binary-analysis tool I have studied since (Crystal(ball), Mini-Me, Ares) recapitulates this layering with different ingredients.

    1.3 Phase A — Static Binary Feature Filter

    Phase A treats every function as a bag of instructions. It scores each by two binary features:

    1. FP density. Fraction of instructions that are floating-point arithmetic. ARM Cortex-M uses the VFPv4 ISA; the relevant mnemonics are vadd.f32, vsub.f32, vmul.f32, vfma.f32, vdiv.f32, vcvt.f32, vldr, vstr.
    2. this-pointer access. Whether the function reads from a small constant offset of the first argument register (r0), which is the C++ ABI signature of a class method dereferencing this->member.

    Pseudo-algorithm:

    def phase_a(elf_path, fp_density_min=5, this_ptr_offsets=range(0, 256, 4)):
    proj = angr.Project(elf_path, auto_load_libs=False)
    cfg  = proj.analyses.CFGFast()
    candidates = []

    for fn in cfg.functions.values():
        insns = list(fn.instructions())
        if len(insns) < 10:
            continue   # too small to be a PID

        fp_count = sum(1 for i in insns if i.mnemonic.startswith(('vadd', 'vmul',
                                                                   'vsub', 'vfma',
                                                                   'vdiv', 'vcvt')))
        if fp_count < fp_density_min:
            continue

        has_this = any(insn_reads_offset_of(i, reg='r0', offsets=this_ptr_offsets)
                       for i in insns)
        if not has_this:
            continue

        candidates.append((fn.addr, fp_count))

    return sorted(candidates, key=lambda x: -x[1])   # rank by FP density

    Why these two features? Because they're the two structural invariants a PID method must satisfy: it does dense math (PID is by definition $K_p\, e + K_i \int e + K_d \dot{e}$) and it stores state across calls (the integrator, the previous error) which it reads off this.

    1.4 Phase B — Dynamic Taint Propagation

    Phase A keeps every function that looks like a PID structurally. Phase B asks whether it behaves like one. Run the firmware in SITL, instrument sensor inputs (gyroscope, accelerometer, GPS) with a taint label, propagate the taint forward through the call graph, and retain only functions that simultaneously:

    1. Read at least one tainted variable (so they are downstream of a sensor), and
    2. Write to an output channel destined for the motor mixer (so they are upstream of an actuator).

    This collapses the set by another order of magnitude, typically from 50–100 to under 10. Critically, it eliminates the EKF inner-state methods (they read sensors but their outputs feed back into other EKF stages, not directly to motors) and the motor-mixing logic (it writes motors but its inputs are already-PID-computed setpoints, not raw sensors).

    1.5 Phase C — SE + SMT AST Matching

    Phase C is the most expensive and the most precise. For each surviving candidate function, symbolically execute it, capture the AST of its output expression in terms of its inputs, and SMT-match this AST against a library of known PID-template ASTs (a literal P, a PI, a PID, a PID with derivative low-pass, a PID with anti-windup, …). The match returns not just “yes / no this is a PID” but which variant, which means downstream tooling can substitute equations symbolically rather than treating the binary as a black box.

    Intuition for the three stages: Phase A asks “does it look like a PID?”, Phase B asks “does it behave like one?”, Phase C asks “is its algebra equal to a PID template?” Each stage is necessary but not sufficient on its own — this is the recurring lesson.

    1.7 How to Read These Numbers Honestly

    Recall @ 10 = 0 % is not a failure of MISMO. It is the design ceiling of Phase A alone. ArduCopter contains roughly 100 high-FP-density routines: EKF predict / update, complementary filter, gyro fusion, Mahony attitude estimator, coordinate transforms (NED ↔ body), motor mixers, low-pass filters, scaling routines. On FP density alone they look indistinguishable from a PID controller. The MISMO paper does not claim that Phase A is sufficient on its own; it explicitly designs Phase A as a wide-net pre-filter for Phase B.

    Recall @ 50 = 60 % is the genuinely useful number: it means Phase A keeps the target in the top ~5 % of the candidate space — a workable starting point for Phase B taint propagation to converge to single digits.

    1.8 What's New in MISMO Versus the Pre-2019 State of the Art

    Before MISMO, the dominant approach to PID identification was either (a) symbol-table extraction (useless against stripped binaries) or (b) source-code instrumentation (useless against deployed firmware). MISMO's contribution is showing that the gap between “I have the binary” and “I can verify the PID is unmodified” can be closed entirely with off-the-shelf binary-analysis primitives, with no source, no symbols, no traces, and no co-operation from the manufacturer.

    The downstream descendants of this idea include Crystal(ball) (DSN 2020), Mini-Me (CCS 2021), and the bit-exact PID equivalence verifier that anchors my CS 8903 project — all of which take a MISMO-identified function as their input.

    2. MAYDAY — Post-Accident Investigation via CVDG

    Paper: Taegyu Kim, Chung Hwan Kim, Altay Ozen, Fan Fei, Zhan Tu, Xiangyu Zhang, Xinyan Deng, Dave (Jing) Tian, Dongyan Xu. “MAYDAY: Identifying Post-Accident Investigation Targets for Drones.” USENIX Security 2020. (Purdue)

    Goal: After a drone crash, given only (i) the last seconds of telemetry from the flight log and (ii) the firmware ELF, point an investigator at the parameter or code change that caused the crash — instead of asking them to manually inspect the ~1000 tunable parameters of a modern flight stack.

    2.1 Why This Is Hard

    ArduCopter exposes roughly 1000 user-tunable parameters: gains (ATC_RAT_PIT_P), filter time constants (ATC_INPUT_TC), failsafe thresholds (BATT_LOW_VOLT), sensor calibrations, geofence radii. Any one of them, set out of range, can crash a drone — often through subtle multi-loop interactions where the surface symptom is several control-loop hops downstream of the root cause. The forensic correlation problem — this telemetry symptom → that parameter — is exactly what MAYDAY automates.

    2.2 The Core Data Structure: Control-Variable Dependency Graph

    The CVDG is the heart of MAYDAY. Built once per firmware version, it is a directed graph that captures every control-flow and data-flow relationship between parameters, internal variables, methods, and output channels.

    CVDG nodes:
    • Parameter nodes — user-tunable values exposed over MAVLink (e.g., ATC_RAT_PIT_P).
    • Internal state nodes — private member variables of control classes (e.g., _pitch_error, _integrator).
    • Method nodes — binary addresses of identified control methods (e.g., the address that nm would call AC_PID::update_all).
    • Output channel nodes — telemetry-observable outputs (e.g., motor_pitch_out, vel_y).

    And four edge types, encoding the dependency direction:

    Edge typeDirectionMeaning
    param_ofparameter → methodthis method reads this parameter at runtime
    binds_toMAVLink name → internal varaliasing across the MAVLink boundary (see §2.3)
    produces_formethod → output channelthis method writes this telemetry channel
    read_byvariable → methodthis method reads this variable

    My reproduced ArduCopter 4.6.x CVDG: 483 nodes, 1498 edges, 80.3 % of nodes bridged to binary addresses via per-binary nm symbol lookup at construction time. The remaining 19.7 % are nodes that exist in source (typically helper inline functions) but get inlined away in the optimised binary — an unavoidable consequence of -O2 compilation.

    2.3 The Subtle Aliasing Problem

    A nasty real-world detail: MAVLink parameter names and internal C++ member names often diverge across firmware revisions. The position-loop velocity D-gain is:

    • Called PSC_VELXY_D in MAVLink parameter dumps (the name a ground station sees).
    • Stored internally as _velxy_d in AC_PosControl.
    • Was renamed from PSC_NE_VEL_D in earlier versions, and at one point through a typo in firmware code was momentarily PSC__NE_VEL_D with a double underscore.

    For the CVDG reverse-walk to work, the binds_to edges have to enumerate every historical alias. My implementation maintains an explicit alias table:

    PARAM_ALIASES = {
    # MAVLink name      : Internal variable name
    "PSC_VELXY_D"       : "_velxy_d",
    "PSC_NE_VEL_D"      : "_velxy_d",   # historical name
    "PSC__NE_VEL_D"     : "_velxy_d",   # typo variant
}

    Missing any alias means the reverse-walk fails silently: the anomaly is detected, the seed method is correct, but the parameter that actually moved (PSC_NE_VEL_D in a 4.4.x log) is never reached because the graph has no edge from internal-variable to historical-MAVLink-name. This was one of the early-stage debugging frustrations in my reproduction.

    2.4 The Pipeline, End-to-End

    Anomaly detection → seed-method lookup → reverse-walk → ranked parameter list.

    (1) Anomaly detection. Run two flights of identical mission profile: a baseline (Phase A) on the audited firmware, and a suspect (Phase B) on the firmware in question. Compute per-channel statistics on both:

    CHANNELS = {
    "pitchspeed_std" : (lambda log: log["ATTITUDE.pitchspeed"].std(),  0.30),  # rad/s
    "vy_std"         : (lambda log: log["LOCAL_POSITION_NED.vy"].std(), 0.025), # m/s
    "horiz_vel_std"  : (lambda log: hypot(log["vx"], log["vy"]).std(),  0.025), # m/s
    # ...
}

ANOMALY_TO_SEED = {
    "pitch_rate_oscillation": "AC_PID::update_all",
    "position_loop_drift"   : "AC_PID_2D::update_all",
    "input_shape_jerk"      : "AC_AttitudeControl::input_quaternion",
}

def detect_anomalies(baseline_log, suspect_log):
    anomalies = []
    for name, (extractor, threshold) in CHANNELS.items():
        base = extractor(baseline_log)
        susp = extractor(suspect_log)
        if susp / base > threshold_ratio(threshold):
            anomalies.append(name)
    return anomalies

    (2) Seed-method lookup. Each anomaly maps to a known seed method address in the CVDG (the ANOMALY_TO_SEED dict above).

    (3) CVDG reverse-walk. From the seed method, BFS backwards through read_by and binds_to edges. Each path back to a parameter node contributes one ranking entry, scored by hop count (fewer hops ⇒ closer to the seed ⇒ higher rank). Implementation sketch:

    def reverse_walk(cvdg, seed_method, max_hops=8):
    visited = {seed_method: 0}
    queue   = deque([seed_method])
    while queue:
        node = queue.popleft()
        if visited[node] >= max_hops:
            continue
        for predecessor in cvdg.predecessors(node, edges={"read_by", "binds_to"}):
            if predecessor not in visited:
                visited[predecessor] = visited[node] + 1
                queue.append(predecessor)
    return sorted(
        [(n, hops) for n, hops in visited.items() if cvdg.node_type(n) == "parameter"],
        key=lambda x: x[1]
    )

    2.5 Worked Example — the PSC_VELXY_D = 0.5 Bug

    ArduCopter 4.6.2 reduced the default value of PSC_VELXY_D from 0.5 to 0.25 in response to user reports of position-loop overshoot. I reverted the value to 0.5 (the historical default) and flew the same 5-waypoint square mission as the baseline, in live SITL. Stages of the pipeline:

    1. Anomaly detection. $\sigma_{v_y}$ jumped from baseline 0.0206 m/s to 0.0306 m/s (factor 1.49×), past the 0.025 m/s threshold → position_loop_drift anomaly emitted.
    2. Seed-method lookup. position_loop_drift → AC_PID_2D::update_all at binary address resolved by per-binary nm.
    3. Reverse-walk. BFS from AC_PID_2D::update_all through read_by edges reaches 7 parameter nodes within 3 hops; _velxy_d is hop-1, the closest. Its alias PSC_VELXY_D is ranked #1.

    Result: rank 1 / 7 — FORENSIC_HIT_RANK_1. The full result JSON is in the project repo at repro/mayday/sitl_runtime/MAYDAY_REAL_BUG_PSC_VELXY_D_RESULT.json.

    2.7 The Two Honest Negatives, Mechanistically

    Both negatives are pipeline boundaries, not pipeline bugs. Each one isolates a specific failure mode of the anomaly-detection layer:

    Bug #3 — test-design direction error. Pull request 32643 reduced the default ATC_INPUT_TC from a high value (sluggish input shaping) toward 0.15. Setting the parameter to 0.01 makes the response more responsive than the new default — the opposite of the historical bug's direction. The flight was smooth because the parameter, while extreme, was extreme in the safe direction. The anomaly detector correctly classified the flight as nominal. The right reproduction would set the value to 0.5 or higher (deliberately sluggish), which would surface as a different anomaly type (input-shaping lag, not yet wired in this reproduction).

    Bug #4 — windup time-scale exceeds probe window. ATC_RAT_PIT_I is the rate-loop integrator gain. Integrator-driven divergence accumulates over time as the windup term grows; the symptom is a slow drift of the actuator setpoint, not a fast oscillation. My probe window was 10 seconds; integrator divergence at 74× default needs ~30–60 seconds to surface above the per-channel noise floor. The anomaly detector cannot distinguish “no problem” from “problem hasn't manifested yet within this window” without a longer probe and a steady-state-error metric — both of which are missing from the current pipeline. The same pattern shows up in 3 of the 15 synthetic ATC_RAT_PIT_I cells, all failing for the same reason. This was predicted in advance based on the synthetic matrix and is the cleanest example of a known structural boundary of the pipeline.

    2.8 An Honest Apples-vs-Oranges Note

    The original MAYDAY paper reports 75 % localisation within 4 hops on private 3DR IRIS+ and MantisQ crash logs — bugs that were genuinely unknown to the investigators at the time. My reproduction operates on known bugs, chosen specifically because they have clean public ground truth (release-note default changes, documented envelope violations). Known-bug reproduction is methodologically much easier than unknown-bug investigation, and the headline numbers should not be compared directly. The contribution of my reproduction is end-to-end pipeline executability on public artefacts and the mechanistic documentation of pipeline boundaries — not a “we beat MAYDAY” claim.

    3. DisPatch — A DSL for In-Field Firmware Patches

    Paper: Taegyu Kim, Aolin Ding, Sriharsha Etigowni, Pengfei Sun, Jizhou Chen, Luis Garcia, Saman Zonouz, Dongyan Xu, Dave (Jing) Tian. “DisPatch: Identification, Disclosure, and Patching of Drone Firmware Configuration Vulnerabilities.” MobiSys 2022.

    Goal: Apply small, tractable, verifiable patches to deployed drone firmware in the field — without recompiling, without grounding the fleet, and without the risk that a hand-written assembly patch destabilises the flight controller.

    3.1 Why a Domain-Specific Language Is the Right Idea

    The naive alternative — ship a hand-written assembly patch as a hot-swap binary blob — has three failure modes:

    1. No formal semantics. A hand-written patch is just bytes; you can prove nothing about it except by exhaustive testing.
    2. Hard to verify. Symbolic execution on arbitrary assembly is intractable when the patch can touch any register, any memory location, any flag.
    3. Hard to insert in place. Variable-length patches require trampoline schemes whose correctness depends on the patcher knowing about every callsite.

    DisPatch observes that the majority of published RAV firmware patches fall into a very small operational vocabulary: clamp a scalar, replace a value, rate-limit a derivative, log a sensor reading. By restricting patches to a DSL targeted at these primitives:

    • Each operation has formal operational semantics ⇒ verification is tractable.
    • Each operation lowers to a small fixed-size Thumb-2 sequence ⇒ in-place trampoline insertion is straightforward.
    • The patch can be proved bit-exact equivalent to the original binary outside the patch region — the gold-standard correctness statement.

    3.2 The DSL Surface (6 Operations)

    OperationOperational semanticsTypical use case
    clamp(var, lo, hi)$\text{var} := \max(lo, \min(hi, \text{var}))$Bound a gain or setpoint
    replace(var, new_val)$\text{var} := \text{new\_val}$Force-override a corrupted default
    log(var, condition)If $\text{condition}$, emit telemetry$(\text{var})$Add forensic instrumentation
    rate_limit(var, max_dv_per_s)$|\Delta \text{var}| \leq \text{max\_dv\_per\_s} \cdot \Delta t$Prevent step changes in setpoint
    vec_clamp(vec, lo, hi)Apply clamp per componentBound a 3-axis setpoint vector
    if_clamp(cond, var, lo, hi)Conditional clamp gated by $\text{cond}$Tighter bound during landing

    3.3 Codegen and Trampoline Insertion

    Each DSL statement is lowered to a Thumb-2 instruction sequence. For clamp(var, lo, hi) on an f32 variable held in s0 with bounds lo, hi loaded into s1, s2:

    vmin.f32   s0, s0, s2     ; s0 = min(s0, hi)
vmax.f32   s0, s0, s1     ; s0 = max(s0, lo)

    Insertion happens via trampoline at the patched function's entry:

    1. The first few bytes of the target function are saved.
    2. An unconditional branch (b.w <patch_region>) is overwritten at the function entry.
    3. The patch region contains the saved prologue + the DSL-lowered Thumb-2 + a branch back to the instruction after the inserted branch in the target.

    The bit-exact-outside-patch-region property is preserved because every byte outside the trampoline and patch region is byte-identical to the original binary, which can be checked by a simple cmp after the patch is applied.

    3.4 Verification Story

    For each DSL operation, the paper provides an operational semantic spec in first-order logic over IEEE-754 floats. A patched function's symbolic execution is checked for two properties:

    1. Within-patch-region correctness: the values flowing through the patch region satisfy the DSL semantics.
    2. Outside-patch-region equivalence: for every input, every byte of the program state outside the patch region is identical to the original binary's state at the same execution point.

    Together these give the strongest possible patch-correctness claim: the patch does what the DSL says and nothing else.

    3.6 What's Explicitly Out of Scope for This Reproduction

    • x86_64 patcher port. DisPatch's native target is ARMv7-M / Thumb-2 (the architecture of every modern Pixhawk). An x86_64 codegen pass is straightforward but unimplemented; it is deferred to a future revision.
    • Live SITL patch injection at runtime. Current reproduction stops at static codegen and emulated execution. Inserting a trampoline into a running ChibiOS image touches scheduler context-save and FPU-state semantics that I have not validated; doing this safely requires a separate engineering pass on the OS-interaction layer.
    • Integration with SAVIOR or RVfuzzer. The original DisPatch paper integrates with these fuzzers to source patch candidates; reproducing that integration is beyond the scope of the directed reading.

    4. Synthesis — The L1 / L2 / L3 Layering

    The three papers are usually presented as independent contributions, but they answer three orthogonal questions about the same object — a PID-based UAV control loop on a stripped binary. The cleanest way I have found to organise the literature is to assign each paper to a layer:

    LayerQuestionMethodOutputRepresentative paper
    L1Which functions implement PID?Static binary features + dynamic taint + SMT AST matchingRanked candidate addressesMISMO
    L2Are two PID-method versions bit-exact equivalent?Symbolic execution + Z3 IEEE-754 FPA solverUNSAT proof or SAT counter-example(my CS 8903 project)
    L3Is the running drone actually behaving normally?Telemetry anomaly detection + CVDG reverse-walkRanked candidate parameterMAYDAY

    4.1 The Three Layers Compose

    • L1 narrows the search space for L2. Running symbolic execution on every function in a stripped binary is impractical (path-explosion times the number of functions). MISMO-style filters reduce ~1000 candidates to under ten before any expensive analysis starts.
    • L2 provides the bit-exact ground truth that L3 needs. If MAYDAY suspects that a deployed binary has drifted from its audited image, an L2 verifier can prove (or disprove) bit-exact equivalence at the PID-method level. Without L2, MAYDAY can only say “something feels wrong”; with L2, it can pinpoint which method's equation has changed.
    • L3 captures what L1 + L2 cannot. Parameters change at runtime — via MAVLink, on every flight, sometimes adversarially. No amount of static analysis can detect a runtime parameter corruption; only telemetry-driven analysis can.

    DisPatch sits orthogonal to all three layers: it is the response mechanism that is triggered when any of L1 / L2 / L3 surfaces a bug. A DisPatch-generated patch can then be re-verified by L2 to confirm it does not break bit-exact equivalence outside the patch region.

    4.2 Where My CS 8903 Project Sits

    The broader CS 8903 project lives on the L2 layer: a bit-exact IEEE-754 FPA symbolic-execution verifier for stripped UAV firmware, currently anchored on 115 / 115 cumulative UNSAT proofs across six boards × six binary perturbations × eleven PID-class methods × three C++ classes × seven mathematical templates. The reproductions documented on this page are the surrounding context: they exercise the L1 and L3 layers end-to-end so that I understand the inputs and outputs each layer expects from L2.

    Each layer informs the others:

    • The L1 ceiling (Phase-A recall @ 10 = 0 %) motivates pairing structural filters with semantic verification — L2's role.
    • The L3 boundaries (windup time-scale, test-design direction) show that even runtime forensics has structural limits that pure simulation cannot resolve.
    • Both observations justify L2: a layer whose claim — bit-exact equivalence over all floating-point inputs — is the strongest of the three and is independently auditable by re-running the SMT proof.

    5. Reproduce It Yourself

    Every reproduction described above is open-source-only on the input side: ArduPilot, PX4, angr, claripy, z3-solver, capstone, keystone-engine. Setup notes below assume a Linux host with Python 3.12, ~32 GB RAM, and ~20 GB free disk.

    5.1 Environment Setup

    # Clone ArduPilot (shallow is fine for SITL-only work)
git clone --depth 1 --recursive https://github.com/ArduPilot/ardupilot.git
cd ardupilot && Tools/environment_install/install-prereqs-ubuntu.sh -y

# Build SITL ArduCopter
./waf configure --board sitl && ./waf copter

# Python environment for the verifier and analysis
python3.12 -m venv .venv && source .venv/bin/activate
pip install angr==9.2.214 claripy==9.2.214 z3-solver==4.13.0.0 \
            capstone keystone-engine pymavlink matplotlib

    5.2 MISMO Phase A on a Stripped ELF

    # Strip a copter binary
arm-none-eabi-strip --strip-all build/sitl/bin/arducopter -o /tmp/arducopter.stripped

# Run the Phase A filter
python repro/mismo/scale/mismo_phaseA_stripped_scale.py \
    --elf /tmp/arducopter.stripped \
    --target AC_PID::update_all \
    --out  /tmp/phaseA_result.json

# Inspect: how many candidates survived, and where the target ranked
jq '.summary' /tmp/phaseA_result.json

    5.3 MAYDAY Pipeline on a Real Bug

    # Launch SITL in one terminal
cd ardupilot && Tools/autotest/sim_vehicle.py -v ArduCopter \
    --console --no-mavproxy --speedup 1

# In another terminal, run the bug driver:
# (this provokes PSC_VELXY_D = 0.5 vs a baseline flight at 0.25)
python repro/mayday/sitl_runtime/mayday_real_bug_psc_velxy_d.py \
    --out /tmp/mayday_bug1.json

# The pipeline runs:
#   1. Baseline flight (40s EKF settle + 60s mission)
#   2. Provoked flight (same mission, PSC_VELXY_D=0.5)
#   3. Compute pre-vs-post anomaly statistics
#   4. CVDG reverse-walk from the seed method
#   5. Rank parameters by hop count
jq '.verdict, .reverse_walk' /tmp/mayday_bug1.json

    5.4 DisPatch Static Codegen

    # Generate Thumb-2 from a DSL file
python repro/dispatch/dispatch_v4_full_dsl.py \
    --dsl  repro/dispatch/full_dsl_surface_test.dsl \
    --arch armv7-m \
    --out  /tmp/dispatch_codegen.json

# Verify round-trip: assemble each op, disassemble, compare
jq '.operations[] | {op, n_insns, n_bytes, roundtrip_ok}' /tmp/dispatch_codegen.json

    5.5 Recommended Order

    1. Get SITL flying a 5-waypoint mission with FlightGear visualisation first (a one-day yak-shave you should not skip — it makes everything else legible).
    2. Reproduce MISMO Phase A. The numbers will surprise you only in how flat they are at @10; that's the lesson.
    3. Reproduce MAYDAY on one real bug (Bug #1 above is the simplest); the alias-table debugging is where the time goes.
    4. Reproduce DisPatch codegen last; it's the most self-contained and the least dependent on a working SITL.
