    Foundational Reading on UAV Firmware Verification

    Directed reading on three foundational papers in stripped-binary analysis, post-accident investigation, and DSL-based patching for unmanned aerial vehicle (UAV) firmware, with local code-level reproductions on ArduPilot and PX4. The three papers share a common substrate — PID-based flight control — and together cover the static / runtime / patch axes of CPS firmware security. This note summarizes each paper's core algorithm, what was reproduced, and how the three layers compose.

    Topics

    1. MISMO — Stripped-Binary Identification of PID Methods
    2. MAYDAY — Post-Accident Investigation via CVDG
    3. DisPatch — A DSL for In-Field UAV Firmware Patches

    1. MISMO — Stripped-Binary Identification of PID Methods

    Paper: Pengfei Sun, Luis Garcia, Saman Zonouz. "MISMO: Multi-Stage Inspection of Mission-Critical Operations on Drones." DSN 2019. (Rutgers)

    Goal: Given a stripped ArduPilot or PX4 ELF (no symbols, no function names — what an attacker or auditor actually obtains), identify which functions implement the mission-critical PID control loops, so that downstream tooling can verify or patch them.

    1.1 The Problem in One Sentence

    A typical ArduPilot ELF contains roughly 800–1000 functions after stripping. Without symbols, every function is just sub_XXXXXX. PID controllers are tiny — tens of lines — and they look superficially like any other floating-point math routine (EKF updates, coordinate transforms, low-pass filters). Brute-force symbolic execution on every candidate is intractable. MISMO proposes a three-stage pipeline that progressively narrows the candidate set.

    1.2 The Three Stages

    Phase A — Static binary feature filter. The simplest signal: a PID controller is dense in floating-point arithmetic and operates on a this pointer (it's a C++ class method). For every function in the CFG:

    1. Reconstruct the control-flow graph with angr's CFGFast.
    2. Count floating-point instructions (e.g., vadd.f32, vmul.f32, vfma.f32) using capstone.
    3. Check whether the function dereferences a this pointer at known C++ offset patterns.
    4. Filter: keep functions with $\text{fp\_density} \geq 5 \;\wedge\; \text{has\_this}$.
    5. Rank surviving candidates by density.

    Phase B — Dynamic taint propagation. Run the firmware in SITL, inject instrumented sensor inputs, and follow tainted variables through the call graph. Only functions that read tainted sensor data (gyro / accel / GPS) and write to actuator output channels survive. This collapses the candidate set further by an order of magnitude.

    Phase C — SE + SMT AST matching. Symbolically execute each surviving candidate; build the AST of its output expression; SMT-match this AST against a library of known PID template ASTs (P, PI, PD, PID, Tlpf variants, …). The match tells you not just "this is a PID" but which PID variant.

    Intuition: Phase A asks "does it look like a PID?"; Phase B asks "does it behave like one?"; Phase C asks "is its algebra equal to a PID template?" Each stage is necessary but not sufficient on its own.

    1.3 Local Reproduction — Phase A Only

    I reproduced Phase A on five stripped ArduPilot ELFs — three ArduCopter releases (4.3.7, 4.4.4, 4.6.3), one ArduPlane, one ArduRover. The target method was AC_PID::update_all, ArduPilot's canonical attitude-rate PID. Results:

    How to read these numbers honestly. Recall @ 10 = 0 % is not a failure of MISMO — it is the design ceiling of Phase A alone. ArduPilot contains ~100 high-FP-density routines (EKF, complementary filters, coordinate transforms, motor mixers); on FP density alone they look indistinguishable from a PID. Recall @ 50 = 60 % means Phase A correctly keeps the target in the top ~5 % of the candidate space — a reasonable starting point for Phase B taint propagation to converge further.

    1.4 Why Phase A Matters Even Though It Alone Misses

    A modern UAV firmware has ~1000 functions. Phase A reliably gets us to ~50–100 candidates without running the binary. Every later, more expensive stage (taint, symbolic execution, SMT) only has to operate on this reduced set. This is the core insight: cheap static filters first, expensive semantic analysis last. MISMO is a clean instance of the broader CPS-security pattern of layered filtering with increasing analytical cost.

    2. MAYDAY — Post-Accident Investigation via CVDG

    Paper: Taegyu Kim, Chung Hwan Kim, Altay Ozen, Fan Fei, Zhan Tu, Xiangyu Zhang, Xinyan Deng, Dave (Jing) Tian, Dongyan Xu. "MAYDAY: Identifying Post-Accident Investigation Targets for Drones." USENIX Security 2020. (Purdue)

    Goal: After a drone crash, given only (i) the last seconds of telemetry from the flight log, and (ii) the firmware ELF, point an investigator at the parameter or code change that caused the crash — instead of asking them to manually inspect ~1000 tunable parameters.

    2.1 The Problem in One Sentence

    ArduCopter alone exposes ~1000 user-tunable parameters (ATC_RAT_PIT_P, PSC_VELXY_D, …). A wrong value on any of them can cause a crash, often through subtle multi-loop coupling. Manually correlating this telemetry anomaly with that parameter is what MAYDAY automates.

    2.2 The Core Data Structure: Control-Variable Dependency Graph (CVDG)

    Built once per firmware version, the CVDG is a directed graph where:

    • Nodes are variables: parameters (ATC_RAT_PIT_P), internal state (_pitch_error), methods (AC_PID::update_all), or output channels (motor_pitch_out).
    • Edges encode the four kinds of control-flow / data-flow relationships:
    Edge typeDirectionMeaning
    param_ofparam → method"this method reads this parameter"
    binds_toMAVLink name → internal varparameter aliasing across the MAVLink boundary
    produces_formethod → output channel"this method writes this output"
    read_byvariable → method"this method reads this variable"

    My ArduCopter 4.6.x CVDG: 483 nodes, 1498 edges, 80.3 % of nodes bridged to binary addresses via nm symbol lookup.

    2.3 The Three-Stage Pipeline

    (1) Anomaly detection. Compute per-channel telemetry statistics on a baseline (Phase A) flight and the suspect (Phase B) flight. If a statistic exceeds a calibrated threshold, an anomaly type is emitted. Examples:

    Anomaly typeThresholdChannel
    pitch_rate_oscillation$\sigma_\text{pitchspeed} > 0.30$ rad/sinner attitude loop
    position_loop_drift$\sigma_{v_y} > 0.025$ m/souter position loop

    (2) Seed-method lookup. Each anomaly type maps to a known seed method:

    ANOMALY_TO_SEED_METHOD = {
    "pitch_rate_oscillation": "AC_PID::update_all",
    "position_loop_drift":    "AC_PID_2D::update_all",
    "input_shape_jerk":       "AC_AttitudeControl::input_quaternion",
    # ...
}

    (3) CVDG reverse-walk. BFS backwards from the seed method through read_by and binds_to edges. Parameters are ranked by hop count (fewer hops → higher rank). Output: top-K parameters.

    2.4 Local Reproduction in Live ArduCopter SITL

    I reproduced MAYDAY end-to-end against four real ArduPilot bugs with public ground truth (release notes + verified envelopes), each provoked in a fresh ArduCopter SITL flight:

    1PSC_VELXY_D = 0.54.6.2 release note (default reduced)$\sigma_{v_y}$  0.0206 → 0.0306 (1.49×)rank 1 / 7 — top-1 hit
    2ATC_RAT_PIT_P = 0.8Verified envelope [0.125, 0.500]$\sigma_\text{pitchspeed}$  0.168 → 1.217 (7.24×)rank 4 / 48 — top-5 hit

    The two negatives are pipeline boundaries, not pipeline bugs.
    • Bug #3 was a test-design error. PR 32643 reduced the default ATC_INPUT_TC, which means the old default was too high (too sluggish). Setting it to 0.01 makes the response more responsive than the new default — the opposite of the historical bug's direction. To reproduce the real failure mode, the value should have been set to 0.5 or higher.
    • Bug #4 was a windup time-scale issue. ATC_RAT_PIT_I is the rate-loop integrator gain; integrator divergence accumulates over time. The 10-second probe window used here is far too short to surface windup-driven divergence.

    2.5 An Honest Apples-vs-Oranges Note

    MAYDAY's original paper reports 75 % localization within 4 hops on private 3DR IRIS+ and MantisQ crash logs — bugs that were genuinely unknown to the investigator at the time. My reproduction operates on known bugs chosen specifically because they have clean public ground truth (release-note default changes, documented envelope violations). Known-bug reproduction is methodologically much easier than unknown-bug investigation, and the headline numbers should not be compared directly. The contribution of this reproduction is end-to-end pipeline executability and the documentation of pipeline boundaries, not a "we beat MAYDAY" claim.

    3. DisPatch — A DSL for In-Field UAV Firmware Patches

    Paper: Taegyu Kim, Aolin Ding, Sriharsha Etigowni, Pengfei Sun, Jizhou Chen, Luis Garcia, Saman Zonouz, Dongyan Xu, Dave (Jing) Tian. "DisPatch: Identification, Disclosure, and Patching of Drone Firmware Configuration Vulnerabilities." MobiSys 2022.

    Goal: Apply small, tractable, verifiable patches to deployed drone firmware in the field — without recompiling the firmware, without grounding the fleet, and without the risk that a hand-written assembly patch destabilizes flight control.

    3.1 Why a DSL Is the Right Idea

    Most published UAV firmware bugs fall into a small number of categories: an unbounded scalar that should be clamped, a stale value that should be replaced, a sensor reading that should be logged before use, a derivative that should be rate-limited. DisPatch observes that this small operational vocabulary is enough to express the majority of real configuration patches. By restricting patches to this DSL:

    • Patches have formal operational semantics, so verification is tractable.
    • Each DSL operation lowers to a small fixed-size Thumb-2 sequence, so binary insertion is in-place via trampoline.
    • The patch can be proved bit-exact equivalent to the original binary outside the patch region.

    3.2 The DSL Surface (6 Operations)

    OperationSemantics
    clamp(var, lo, hi)Scalar bound
    replace(var, new_val)Direct overwrite
    log(var, condition)Conditional telemetry emission
    rate_limit(var, max_delta_per_sec)Rate-of-change bound
    vec_clamp(vec, lo, hi)Per-component clamp on a vector
    if_clamp(cond, var, lo, hi)Conditional clamp

    3.3 Local Reproduction — Static Codegen Surface

    I built a static codegen surface covering all six operations. Each DSL statement compiles to a Thumb-2 instruction sequence that is then trampoline-inserted at the patched function's entry. Example input:

    clamp(target_pitch_rate, -1.0, 1.0)
rate_limit(roll_setpoint, 90.0)
if_clamp(in_landing, throttle_out, 0.1, 0.6)

    Codegen output across the full 6-operation surface test:

    MetricValue
    Operations covered6 / 6
    Total Thumb-2 instructions emitted86
    Total binary patch size226 bytes
    Round-trip verificationkeystone-engine assemble & capstone disassemble all valid
    Explicitly out of scope for this reproduction.
    • x86_64 patcher port (the paper’s native target is ARMv7-M / Thumb-2; x86_64 codegen is a straightforward extension I have deferred).
    • Live SITL patch injection at runtime — the current reproduction stops at static codegen + emulated execution. Inserting a trampoline into a running ChibiOS image touches scheduler and FPU context-save semantics that I have not validated.
    • Integration with SAVIOR or RVfuzzer (the original paper’s evaluation harnesses).

    4. Synthesis — The L1 / L2 / L3 Layering

    The three papers are usually presented as independent contributions, but they answer three orthogonal questions about the same object (a PID-based UAV control loop). One way to see the field clearly is to organize them into three layers:

    LayerQuestionMethodOutputRepresentative paper
    L1Which functions implement PID?Static binary feature filters + dynamic taint + SMT AST matchingRanked candidate addressesMISMO
    L2Are two versions of a PID method bit-exact equivalent?Symbolic execution + Z3 IEEE-754 FPA solverUNSAT proof or SAT counter-example(verifier — see below)
    L3Is the running drone actually behaving normally?Telemetry anomaly detection + CVDG reverse-walkRanked candidate parameterMAYDAY

    The three layers are independent and composable:

    • L1 narrows the search space for L2. Running symbolic execution on every function in a stripped binary is impractical; MISMO's filters reduce ~1000 candidates to ~50.
    • L2 provides the bit-exact ground truth that L3 needs. If MAYDAY suspects that a deployed binary has drifted, an L2 verifier can prove (or disprove) bit-exact equivalence against the audited binary.
    • L3 captures what L1 + L2 cannot. Parameters change at runtime — via MAVLink, on every flight. No amount of static analysis can detect a runtime parameter corruption; only telemetry-driven analysis can.

    DisPatch sits orthogonal to all three layers: it is the response mechanism that triggers when any of L1 / L2 / L3 surfaces a bug.

    4.1 Where My CS 8903 Work Sits

    My broader CS 8903 project is on the L2 layer: a bit-exact IEEE-754 FPA symbolic-execution verifier for stripped UAV firmware (currently anchored on 115 / 115 cumulative UNSAT proofs across six boards, six binary perturbations, and eleven PID-class methods). The reproductions on this page document my engagement with the L1 and L3 layers as the surrounding context for that work. Each layer informs the others:

    • The L1 ceiling (Phase A recall @ 10 = 0 %) motivates pairing static filters with semantic verification.
    • The L3 boundary (windup time-scale exceeds the probe window) shows that even runtime forensics has structural limits that pure simulation can’t resolve.
    • Both together justify L2: a layer whose claim — bit-exact equivalence over all floating-point inputs — is the strongest of the three and is independently auditable.
